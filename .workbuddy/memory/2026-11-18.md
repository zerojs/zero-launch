### 第五批：顶部两个按钮的间距与右边距

**间距**：`HStack(spacing: 8)` → `20`。
根因不是 spacing 小，而是 `HeaderToolbarButton` 的 hover 底衬用了 `.padding(-6)`，
画出来比 32pt 的图标大一圈（44pt）。spacing 8 时两个底衬直接叠 4pt，看着像连成一条；
20 时中心距 52、底衬 44，留出 8pt 实际空隙。

**右边距**：头部原本用系统默认 `.padding(.horizontal)`（约 16pt），
和网格的留白各算各的 → 按钮比 app 更贴边。
改成与网格同一套算法：

```swift
let iconInset = max(0, (currentColumnWidth - currentIconSize) / 2)
let headerHorizontalInset = max(actualHorizontalPadding + iconInset, 24)
```

关键点：网格内容边缘只是 `actualHorizontalPadding`（全屏 = 4% 画布宽），
但 app 是在列宽里**居中**的，肉眼看到的图标右缘还要再缩进 (列宽-图标宽)/2。
`currentColumnWidth` / `currentIconSize` 由 `captureGridGeometry` 在网格布局后回填，
首帧为 0 时先按内容边缘排，下个 runloop 自动校正（会有一次 ~20pt 的轻微跳动）。
典型 1512×982 全屏：60.5 + (181.6-140.7)/2 ≈ 81pt，改动前是 60.5+16 ≈ 76.5pt。
**这个 (列宽-图标宽)/2 的修正被用户截图打回：实测按钮偏左约 20pt。**
CA 渲染器给每个 app 的 item 宽度基本贴着图标，图标并不在整列宽度里居中留白，
所以只该对齐「网格内容边缘」= `max(actualHorizontalPadding, 24)`，不要加那半格。
教训：网格是 CANAL 渲染的，SwiftUI 侧算出来的 columnWidth/iconSize 不能直接
拿来推断图标在各列里的位置；对齐这类问题必须按截图实测像素反推，不能按公式推。

### 第六批：改行列数后图标重影（幽灵层）—— 真 bug 修复

**现象**：调每行/每列数量后，屏幕上同时叠着两套尺寸、两套位置的图标和标签
（用户截图：整屏 app 像被复制了一层，标签字号都不一样）。

**根因**：`CAGridView+Layout.swift` 的 `reconcileLayers` 里
`guard idx < items.count else { break pageLoop }`。
`break pageLoop` 会连下面那行 `newPageLayers.append(pageLayers)` 一起跳过 ——
整页的层虽然还挂在 `pageContainerLayer` 上、且已被记进 `reused`（所以不会被删），
却不再被 `iconLayers` 记录 → 变成**永远不会被清理的幽灵层**：
它们停在旧的位置和旧的图标尺寸上，下次 `rebuildLayers()` 只清 `iconLayers` 里
记录在案的层，幽灵层原地留着，新层再叠上去。

**触发条件**：改行列数后 `previousPageCount`（用**新的** ipp 算旧 items 的页数）
与 `pageCount` 恰好相等，于是走进差量路径。比如 40 个应用、ipp 从 35 变 42：
两边都算出 1 页 → 走进差量 → 第 40 个 item 处 break → 40 层全成幽灵。

用 `/tmp/reconcile_test.swift` 复刻控制流验证：

| items | ipp | 旧代码 页结构 / 幽灵层 | 新代码 |
|---|---|---|---|
| 40 | 35 | [35] / **5** | [35, 5] / 0 |
| 40 | 42 | [] / **40** | [40] / 0 |
| 40 | 36 | [36] / **4** | [36, 4] / 0 |
| 13 | 35 | [] / **13** | [13] / 0 |

**三处修复**
1. `break pageLoop` → 只 `break` 内层，内层结束后照常 append，再判断是否还有 item。
2. 新增 `layersItemsPerPage`，记录这棵层树是按多少格/页建的；
   `reconcileLayers` 的 guard 改为 `layersItemsPerPage == ipp && pageCount == iconLayers.count`

### 第七批：拖拽优化"消失"的诊断

**结论：代码没被删，是渲染器被切走了。**

`defaults read com.roversx.launchnext` 实测：
```
performanceMode = lean
useCAGridRenderer = 0
```
即「轻量」模式 + CA 网格渲染关闭 → 网格走 SwiftUI 的 `LazyVGrid` 路径。
而这两个「拖拽优化」只存在于 CA 路径：
- 预览不带文件名：`LaunchpadView.swift:988` 的 `DragPreviewItem(..., showsLabel: false)`
  —— 在 `if appStore.useCAGridRenderer` 分支里；
- 边缘翻页提示条：`CAGridView+EdgeHint.swift` + `EdgeHintController`，
  SwiftUI 网格里根本没有对应实现。

`git diff` 全量确认：本轮改动里没有任何一行删除 drag / edge / preview 相关代码。

**真正的陷阱**（已修）：`AppStore.performanceMode` 的 didSet 里，
切到 `.full` 时执行 `useCAGridRenderer = false`，而这个 setter 会把它写进磁盘。
切回 `.lean` 时没有任何恢复逻辑 —— 只要来回切过一次性能模式，
CA 网格就永久关闭，所有 CA-only 的交互（拖拽优化、长按卸载抖动）一起消失。

修法：新增 `caGridSuspendedByFullMode` 标记。`.full` 强制关 CA 前先记一笔，
`.lean` 时若该标记存在就自动恢复 `useCAGridRenderer = true` 并清标记。
用户手动关掉 CA 的情况下标记不存在，不会被"好心"打开。

**同时补齐 SwiftUI 路径的两处差距**（不再依赖用户必须开 CA）：
1. `LaunchpadView.swift:1071` 的 `DragPreviewItem` 补 `showsLabel: false`；
2. 新增 `LaunchNext/EdgeHintOverlay.swift`：`NSViewRepresentable` 包一个真实 NSView
   宿主，复用**同一个** `EdgeHintController`（不另写 SwiftUI 版），
   `hitTest` 返回 nil 保证不抢拖拽手势；`layout()` 里重摆（首帧 bounds 为 0 的坑）。
   朝向由 `@State dragEdgeHintSide` 驱动，在 `applyDragUpdate` 里按
   `config.pageNavigation.edgeFlipMargin` 判定（与 flipPageIfNeeded 同一套边界条件），
   手势 `.onEnded` + `.onChange(of: draggingItem == nil)` 双保险收起。

## 【重要】命令行构建的宏沙箱问题已解决

之前「xcodebuild 无法编译」的结论**是错的**：根因是 swift-plugin-server 加载 SwiftUI 宏时
调用 `sandbox-exec` 被系统拒绝（`sandbox_apply: Operation not permitted`），与 WorkBuddy 会话
沙箱无关（dangerouslyDisableSandbox 也不行）。

**解法：给编译器传 `-disable-sandbox`**（swiftc / SwiftPM `--disable-sandbox` 的同款 flag，
禁用宏插件的沙箱加载）：

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild \
  -project LaunchNext.xcodeproj -scheme LaunchNext \
  -configuration Debug -destination 'platform=macOS,arch=arm64' \
  -derivedDataPath build/DerivedData \
  OTHER_SWIFT_FLAGS='-disable-sandbox' build
```

用 `-disable-sandbox` + 增量缓存 32s 就 BUILD SUCCEEDED。已部署到 `/Applications/ZeroLaunch.app`
并启动（PID 8439）。后续所有「构建最新」都走这条命令，不再需要用户去 Xcode GUI 手动 ⌘R。
